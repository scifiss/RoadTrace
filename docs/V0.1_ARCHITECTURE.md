# RoadTrace V0.1 architecture

## Product boundary

RoadTrace accepts one strictly validated public GitHub HTTPS URL, clones a bounded
snapshot and history into an application-owned temporary directory, performs
read-only static analysis, and returns an auditable reverse roadmap. It never
imports, builds, installs, or executes anything from the analyzed repository.
Private repositories, arbitrary Git remotes, local paths, and future planning are
outside V0.1.

## Shape of the system

```text
React/Vite client
      │ JSON/REST
      ▼
FastAPI boundary ── SQLite result store
      │
      ▼
Analysis orchestrator
  ├── safe GitHub clone + bounded file inventory
  ├── Python AST / JS+TS Tree-sitter analyzers
  ├── structural, dependency, workflow, and data-hint graphs
  ├── bounded Git history extraction
  ├── deterministic capability inference + taxonomy
  ├── evidence-dimension maturity calculation
  └── optional Responses API semantic refinement
```

The backend is a single process and the frontend is a static single-page app.
Long-running production analysis should eventually move behind a durable job
boundary, but an in-process request keeps this first vertical slice small.

The client presents capability discovery in layers: compact category and metric
summaries establish orientation, the constellation maps repository → category →
capability, and code/workflow/data projections default to a bounded overview or a
one-hop selected-node neighborhood. A two-hop view and the complete backend-bounded
projection require explicit user action, keeping deep evidence available without
making the initial graph unreadable.

## Evidence model

The persisted `AnalysisResult` deliberately separates three layers:

1. `evidence`, `entities`, `relationships`, and `commits` are observed facts.
2. `capabilities`, maturity signals, and timeline events are interpretations.
3. `graphs` and category summaries are presentation projections.

Every capability carries one or more observed evidence IDs, a bounded reasoning
summary, confidence, first/last dates, and an explicit maturity state. LLM output
cannot introduce evidence IDs, categories, or capabilities that are not grounded
in the deterministic candidate set. Malformed or failed semantic output is ignored.

## Analysis pipeline

1. Parse and canonicalize `https://github.com/{owner}/{repo}`.
2. Clone with an argument-array subprocess, shallow history limit, partial blob
   filtering, disabled hooks, no submodules, a timeout, and a size budget.
3. Walk without following symlinks; ignore dependencies, VCS data, binaries,
   generated output, bundles, and lockfiles; enforce file and byte limits.
4. Extract modules, classes, functions/methods, imports, calls, routes, components,
   schemas, and test symbols. Resolve relationships when possible and retain
   honest confidence on best-effort edges.
5. Identify entry points and retain only bounded call neighborhoods as inferred
   workflows. Record schema producer/consumer relationships as data-flow hints.
6. Sample bounded Git metadata across the reachable history and read changed-path
   summaries without checking out or running historical code. Map capability evidence
   paths to their earliest and
   latest observed changes.
7. Create deterministic, taxonomy-aligned capability candidates. Calculate
   maturity from named evidence dimensions rather than an invented percentage.
8. If both `OPENAI_API_KEY` and `OPENAI_MODEL` exist, send only a bounded structured
   evidence digest through the official Responses API and validate it with
   Pydantic. The deterministic result remains available on any failure.
9. Persist the complete result as JSON in SQLite and return it to the client.

## Extension seams

- `LanguageAnalyzer` is the interface for new AST adapters.
- Capability rules operate on normalized entities/evidence, not parser internals.
- Repository acquisition is injected into the service for isolated tests.
- The result schema is UI-agnostic and suitable for a future background worker.
- Graph projections are bounded independently from the underlying evidence store.

## Security invariants

- Only exact GitHub HTTPS repository URLs are accepted; ports, credentials,
  fragments, queries, SSH syntax, file URLs, and path traversal are rejected.
- Repository commands use `subprocess` argument arrays with `shell=False`.
- Clone never recurses into submodules and Git hooks are redirected to a known
  empty directory.
- Analysis opens only regular files beneath the clone root and never follows
  symlinks.
- No package manager, interpreter, build tool, test runner, or repository script is
  invoked against untrusted content.
- Limits are environment-configurable and truncation is visible in result warnings.
- Temporary clones are removed by `TemporaryDirectory` on success and failure.

## Known V0.1 approximations

Static call resolution is lexical and bounded, not compiler-grade. JavaScript and
TypeScript type resolution does not span package exports. Workflow and data-flow
graphs are explicitly labelled inferred. Depth-bounded history can omit older origins
in very long-lived repositories, and that boundary is surfaced as a warning. GitHub
PR/issues metadata is not fetched. SQLite and
synchronous requests target local/single-user use.
